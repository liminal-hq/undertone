# M7: Outputs

## Objective

Undertone produces sound without Web Audio: natively in real time, in a browser `AudioWorklet` (opt-in), and in a no-browser render through WASI, Node, Bun, and Deno.

**Depends on:** RF-22 (M5) for native output, RF-22 and RF-25 (M6) for the worklet, RF-20 (M4) and RF-25 (M6) for the no-browser render. The native output can start before M6 finishes. **Done when:** each backend meets its acceptance.

## Work packages

### RF-28. Native real-time output (`undertone-native`, `cpal`)

- **Owner:** A. **Size:** M. **Depends on:** RF-22.
- **Objective:** a `Sink` trait after `Engine`, and `undertone-native` playing on `cpal` with a control thread booking windows into a lock-free ring (`rtrb` or `ringbuf`, licence checked with `cargo deny`, D-11) and pooled voices.
- **Steps:** (1) the `Sink` trait in the engine's output seam; (2) `crates/undertone-native` with the `cpal` stream, the ring, and the audio-thread runner; (3) an example `cargo run -p undertone-native --example play`; (4) **documentation:** rustdoc, and a "Playing natively" page in the Rust guide (`docs/guide/rust-native.md`).
- **Acceptance (formerly spike R7):** no underrun for ten minutes with every core busy; zero allocations on the audio thread (counted); position error under 1 ms; the example plays a pattern. State plainly whether it was listened to. For hosts that own their own application loop (a Tauri plugin, TAU-01 in [HANDOFFS.md](../HANDOFFS.md)): the native output opens and closes cleanly on request (a test opens and closes it twice), a host can supply its own audio callback through the `Sink` seam instead of the `cpal` handling, devices can be listed and selected, and the Linux build prerequisites (for example the ALSA development headers) are written in the crate's README and the CI job.
- **Risks:** device availability in CI (the soak test runs by hand on the person's machine, not in CI); the `cpal` licences and system libraries (checked by `cargo deny` and documented).

### RF-29. The worklet backend (`undertone-worklet`)

- **Owner:** A builds; P runs the device checks. **Size:** L. **Depends on:** RF-22, RF-25.
- **Objective:** an opt-in browser backend: the render module (`crates/undertone-wasm-render`, D-47) inside an `AudioWorkletProcessor`, with a small `TextDecoder` shim because the worklet scope lacks one; booking on the main thread or a worker, the worklet playing booked records only (D-48); the main thread compiles the module and posts the `WebAssembly.Module` in `processorOptions`; a ring over `SharedArrayBuffer` when cross-origin isolated, `MessagePort` otherwise.
- **Steps:** (1) the `TextDecoder` shim and the record ring; (2) the processor and the bridge's backend switch in `packages/undertone`; (3) a harness page that reports underruns, the 99th percentile of `process`, and drift; (4) **documentation:** a worklet section in `docs/guide/runtimes.md` (opt-in, cross-origin isolation, the foreign-leaf restriction), and the measured numbers.
- **Acceptance (formerly spike R6):** on a mid-range phone, a Steam Deck, and Chromium throttled six times (the person runs them with the harness page), no underrun over five minutes, the 99th percentile of `process` at most 40% of the 128-frame budget, drift zero against frames. If not met, the backend still ships as opt-in with the numbers documented, and Web Audio stays the default (D-09).
- **Risks:** the device checks need the person's time (batched into one request). A pattern with a foreign leaf does play in the worklet: D-48 collects the voices on the main thread, so the leaf is queried there and nothing is refused.
- **From M2 ([DESIGN-ADJUSTMENTS.md](../results/DESIGN-ADJUSTMENTS.md)):** decide whether the worklet queries patterns or only plays booked voices before RF-24 fixes the combined budget: the pattern core is about 65 KB of the measured worklet (R4), so the answer moves the combined limit by about 70 KB (D-07).

### RF-30. Rendering with no browser (WASI, Node, Bun, Deno)

- **Owner:** A. **Size:** S. **Depends on:** RF-20, RF-25.
- **Objective (formerly spike R8):** render a pattern to WAV under `wasmtime` (`wasm32-wasip1`, a small CLI in `crates/undertone/examples/` or `crates/undertone-cli`), and through the package in Node 20, Bun 1.2, and Deno with no Web Audio.
- **Steps:** (1) the WASI build and CLI; (2) the same render through the package in each runtime; (3) a CI job that builds the WASI target; (4) **documentation:** a "Rendering without a browser" section in `docs/guide/rendering-and-export.md` (and a Rust counterpart), with the commands.
- **Acceptance:** the same bits as the native render, or within R9's tolerance; a CI job builds the WASI target.

## Platforms

The pure crates are checked for ARM64 (tests, from M2) and FreeBSD (`cargo check` for `x86_64-unknown-freebsd`, from M2) in CI. In this milestone: build and test `undertone-native` on ARM64 Linux (the `ubuntu-24.04-arm` runner and the shared `ci-rust` image, which is published for both architectures); decide whether `cpal` gives FreeBSD an output (its ALSA-compatible and OSS paths are unverified, so this is an open question for RF-28) and, if it does, run the tests in a FreeBSD virtual machine with a third-party action pinned by commit SHA; and list Apple silicon and Windows on ARM in the release matrix (M8) with what was and was not run.
