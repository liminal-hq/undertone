# R4: size and build time

Spike R4 (RF-11) on `chore/spike-r4-size-and-build-time`, based on `chore/spike-r2-handles-and-closures`. The question: do the two WebAssembly modules fit the D-07 budgets (control at most 150 KB, worklet at most 200 KB, together under 300 KB, all after Brotli), and do the builds stay under 30 s (incremental) and 2 minutes (clean)?

## Verdict

**Pass with conditions.** Every threshold passes on what was built, with wide margins, but what was built is a lower bound: the engine's voice graph, the chords, and 49 of the 53 controls do not exist in Rust yet, and the extrapolation to the whole API puts the control module near its 150 KB limit, and the two modules together near 300 KB if the worklet carries its own copy of the pattern core. The conditions:

1. **The measured modules are far under budget.** The control module is **83,695 bytes** after Brotli 11 (limit 150,000) and the worklet is **75,767 bytes** (limit 200,000); together **159,462 bytes** (limit 300,000). Incremental builds take 1.6 to 2.3 s (limit 30 s) and a clean release build of both modules takes 9.2 s (limit 120 s).
2. **The extrapolation is tight, and one design choice decides it.** From the minified TypeScript sizes of what is missing, the whole API is about **148 KB** for the control module (127 to 168 KB across the low and high cases). The worklet is about **145 KB** (116 to 175 KB) if it carries the pattern core as `ARCHITECTURE.md` lists it (`undertone-worklet` depends on the pattern crate), and **74 KB** (48 to 102 KB) if it does not, which RF-29 allows because it books on a worker or the main thread. Together that is **293 KB** (243 to 343 KB) with the core in both modules and **222 KB** (174 to 270 KB) without it in the worklet. The pattern core is about 65 KB of the worklet after Brotli, measured. The combined 300 KB budget is the one most likely to fail, and only in the first case.
3. **The budgets cannot become failing CI checks with a fixed number until RF-24 has a real module.** This file proposes numbers (see "What it changes"); the person sets them.
4. **`wasm-opt` is not in the shared CI images or on this machine.** A working one came from the `binaryen` npm package (see "What was run"); D-22 should include it.

KB in this file are 1,000 bytes. Every pass or fail below is the same at 1,024.

### The extrapolation to the whole API

R1's crate is the real pattern core, so it is measured as built. What is **not in it yet**, and how each part was estimated (`spikes/r4-size/extrapolate.py`, which prints these figures):

- **Chords and voicing** (`chord.ts`, 102 lines; R1 covers 308 of 309 programs, the missing one being `chord()`): a small part; estimated with the other missing logic below.
- **The other 49 controls** (the crate has `gain`, `lpf`, `pan`, `attack` as a four-way enum): the stubs cost 3.4 KB raw (0.6 KB after Brotli) for 53 exports. The real per-control validation and sanitising messages are estimated at 10 KB raw.
- **The engine's voice graph and booking** (`engine.ts`, `instruments.ts`, `effects.ts`, `masterBus.ts`, `noise.ts`, `waves.ts`, `pitchCurve.ts`, `score.ts`, and half of `panPath.ts`, `autopan.ts`, and `surround.ts`, whose maths are already in the engine crate): 21,640 minified TypeScript bytes. Drift, chord, and the unported part of scale: 2,549 bytes. Offline rendering, WAV encoding, and the scheduler's timing (`render.ts`, `wav.ts`, `scheduler.ts`): 7,808 bytes, counted only in the control-with-render case.
- **How:** a ratio of raw WebAssembly bytes to minified TypeScript bytes, measured on what is ported. The pattern core is 27,726 minified TypeScript bytes (`pattern`, `fraction`, `mini`, `signal`, `random`, `control`, `pitch`, `scale`); the pattern-only module is 201,300 raw bytes, 160,300 after taking out about 41 KB of fixed overhead, so **5.8 raw bytes of WebAssembly per minified TypeScript byte** (central). The low case is 3.5 (Rust that is tighter than the pattern core, which carries exact `i128` fractions and string formatting) and the high case 8.0 (verbose graph-operation enums). Brotli takes raw to 0.38.
- **Software signal processing:** the TypeScript's DSP is the browser's Web Audio nodes; the worklet must implement oscillators, filters, delays, the convolution reverb, the FM voice, and sample playback itself. There is no TypeScript to scale from, so this is **a judgement: 25, 45, and 70 KB raw** (low, central, high), against 3.3 KB for this spike's one-voice renderer. If `renderToBuffer` runs in the control module's engine (D-14), that code is in the control module too (the last column).

## What failed and why

Nothing failed a threshold. The things that did not work or were not as expected:

- **`wasm-opt` is not available.** It is not installed, not in the shared CI images (ARCHITECTURE.md lists `ci-rust` as providing Rust, rustfmt, Clippy, `cargo-nextest`, `cargo-deny`), and the first `npm i binaryen` with a guessed version failed (`^126.0.0` does not exist; 132.0.0 is the current one). The npm package works and needs only Node, so it is the fallback taken. It does not need building from source.
- **`wasm-opt` barely matters after Brotli.** It cuts raw size by 11%, but only 1 to 2% after Brotli, so the budgets (measured after Brotli) are nearly independent of it. The step is worth keeping for the raw size (parse and compile time) and costs 1.5 s.
- **Feature gates save less than the plan implies.** Gating the exports of scales, signals, and the engine's maths saves 4.5, 1.2, and 1.2 KB. Gating the real code would save somewhat more (a `scales` feature also removes the `Scale` map node and the tables; signals' nodes are 1,474 function bytes), but not enough to change a verdict. The levers that matter are the ones the plan has not named: **the mini-notation parser out of the worklet (-7.4 KB)** and **`serde_json` kept out (-16.3 KB against the comparison)**.
- **The pattern core is heavy for what it is.** It is 76 KB after Brotli alone, against 8.8 KB for the matching TypeScript (a ratio of 8.7). About a quarter of it is fixed Rust overhead (`core::fmt`, `core`, `std`, `alloc`, `compiler_builtins`). Two places to look were not measured: `core::fmt` (17.8 KB of function bytes, which the float formatting for JavaScript number strings and the `Display` of the tree draw in), and D-13's `i128` fraction (the 128-bit arithmetic itself is only 2.3 KB in `compiler_builtins`, so the saving would be in the code around it, not in the arithmetic).
- **The two modules duplicate the pattern core, if both carry it.** The control module cannot share it with the worklet (separate WebAssembly instances on separate threads), so the combined budget pays for the core twice. Measured: the worklet with its pattern exports switched off (a `pattern` feature) is 26,875 bytes raw and 10,432 after Brotli, so the core is about 65 KB of the 75.8 KB worklet.

## What it changes

- **D-07 stands as written for the two per-module budgets on today's evidence, but I propose these numbers for RF-24** (the person decides; the plan files were not edited):
  - **Control 150 KB and worklet 200 KB, unchanged, as failing checks** (after Brotli, the `.wasm` only).
  - **Together: 300 KB stays if the worklet carries no pattern core (extrapolated 222 KB, high case 270 KB); 350 KB if it does** (the sum of the two per-module limits; the extrapolated high case is 343). Keeping 300 with the core in both modules would make the combined check the first to fail for a reason (the duplicated core) that no feature can remove. RF-29 should decide where booking runs before RF-24 fixes the number.
  - **Early-warning thresholds at 90% of each (135 and 180 KB, and 270 KB or 315 KB together)** that print in the CI summary but do not fail, so growth shows before it breaks.
  - **A re-measure of the real modules at the end of RF-24 and again at RF-29** before the limits are final; if the real control module is over 150 KB, the order of response is: keep rendering out of it, gate `scales`, `chords`, and `signals` behind cargo features and optional sub-modules (per D-07 and RF-11's fail changes), then ask for a limit near 200 KB (control) and 400 KB (together).
- **The control exports are generated from one table** (API-MAPPING.md, decision "One table drives the controls"): the three-export dispatcher is as cheap as 53 named exports (0.6 KB), so the bridge may call either; the generated TypeScript methods are the less brittle choice.
- **The worklet should carry no pattern core if booking runs elsewhere (RF-29's text allows it), and in any case no text parser:** the core is about 65 KB of the measured worklet, and the mini-notation and scale parsers alone are 7.4 KB. Add the question "does the worklet query patterns or only play booked voices?" to RF-29's objective; the answer moves the combined budget by about 70 KB.
- **`wasm-opt` for CI (D-22):** add `binaryen` (the npm package, Node only) to the CI job's tools, or a prebuilt binary to the shared image; the build script `scripts/build-wasm.sh` must run it with `-all`.
- **`serde_json` never enters the control module** (+16.3 KB for the same data); `serde-wasm-bindgen` is +7.2 KB and stays as planned.
- **No change** to ARCHITECTURE.md, API-MAPPING.md, or the milestone documents. The size-budget bullet in ARCHITECTURE.md and D-07 should be updated if the person accepts the proposed numbers.

## What was not verified

- **Nothing was listened to.** Neither module was executed (R2 ran its own binding in five runtimes; this spike only built, optimised, and measured).
- **The figures for the whole API are estimates.** The engine's voice graph, the chords, 49 of the 53 controls, rendering, and the software DSP do not exist in Rust yet, so the measured worklet and control figures are **lower bounds**. The extrapolation rests on one measured ratio (5.8 raw bytes per minified TypeScript byte, taken from the pattern core, which has unusually heavy code) and a judgement (25 to 70 KB of software DSP). A different ratio moves the control module from 127 to 168 KB.
- **The worklet's renderer is a stand-in** (one oscillator, an envelope, a one-pole filter, the pan law), and its `build` byte program is not a tree deserialiser; a real one adds code (the serialised form of every node and the foreign-function table).
- **Build times of the finished crates** (the extrapolation above is a multiple of today's, not a measurement), cold-cache builds, builds on CI hardware, and builds on other machines.
- **WebKit, the browsers, and load time** (compiling a 220 KB module): not measured; R3 covers loading.
- **Brotli at the server.** The sizes are the files compressed at quality 11; a host that compresses at a lower quality sends more bytes.
- **The attribution** is one unstripped build of the worklet and credits generic code to the crate that instantiated it; the control module's split was not taken.
- **Other levers not tried:** `-Z build-std` with `panic_immediate_abort` (nightly only), a custom allocator (`wee_alloc` and similar, unmaintained), removing `core::fmt` from the core, an `i64` fraction (D-13), and a shared core between modules.
