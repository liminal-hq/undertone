# RF-16: signals, the serialised tree, and the benchmark

RF-16 on `feat/rust-signals-checks`, based on `feat/controls-and-resolve-params`. The signals themselves passed layer 1's `signals` group (104 of 104) since spike R1; what this package added is the acceptance checks, the off-main-thread check (formerly R11), and the documentation.

## Verdict

**Pass.** A tree holding signals serialises to a short text, rebuilds on another thread, and answers every query and every sample exactly as the original does. The Rust query is at most the TypeScript's figure on the same machine. Two behaviours the corpus did not pin now have Rust tests.

## What the acceptance was missing

- **Mixed continuous and discrete compositions (`5a45f43`):** the corpus holds raw queries of `cat`, `seq`, `timecat`, `stack`, `arrange`, and `every` with a continuous and a discrete child (`signals-cat-mixed-01` and its siblings), but never a control reading one through cut query windows, which is where the bug was. `tests/signal_regressions.rs` builds the reference's eleven compositions, reads `note("c4*8").pan(...)` over four cycles as 1, 2, 3, 8, and 16 windows, and checks the values equal each other and equal what the TypeScript gives (run with `bun` on `src/index.ts`, no `bun install`).
- **Negative time from a signal (`6deecfb`):** the corpus case `signals-attack-negative` samples `sine2` at 0 and 1/2, which never goes below zero, so the rule was untested. The same test file gives all thirteen duration controls a signal that reads -1 (the key stays unset) and 0 (kept), checks that `nudge`, `late`, and `early` stay signed, and that 1e300 is left alone. The warning itself stays with the host, as the controls module says.

## The serialised form

`Pattern::serialize` and `Pattern::deserialize` (`crates/undertone-pattern/src/serialize.rs`): text, deterministic, `no_std + alloc`, no dependency, no `serde`. A `ut1` header and the tree in prefix order, tokens separated by single spaces; a number is Rust's shortest exact `{:e}` form (every `f64` keeps its bits), a string is its byte length, a colon, and the bytes, a fraction is `n` or `n/d`. The `Wire` trait says how a value type (`f64`, `bool`, `Value`) is written. The module's rustdoc lists the tags.

| Tree                                                                 | Text                                                                                                                                                                    | Bytes |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----: |
| `sine.range(200, 2000).segment(4)`                                   | `ut1 sg 4 map range 2e2 2e3 sig per sine 1 n 0e0`                                                                                                                       |    47 |
| `rand.seed("kick")`                                                  | `ut1 sig rand s 4:kick`                                                                                                                                                 |    21 |
| `cat(rand.range(0, 1), perlin.segment(8))`                           | `ut1 ct 2 map range 0e0 1e0 sig rand n 0e0 sg 8 sig perlin n 0e0`                                                                                                       |    63 |
| `note("c3*4 e3").lpf(sine.range(300, 3000)).pan(rand.range2(-1, 1))` | `ut1 wc pan p wc lpf p st 2 cp 0 1/2 fa 4 p m 1 5:pitch s 2:c3 cp 1/2 1 p m 1 5:pitch s 2:e3 map range 3e2 3e3 sig per sine 1 n 0e0 map range2 -1e0 1e0 sig rand n 0e0` |   165 |

It covers every node a signal tree can hold and the rest of the data nodes: all signal kinds with their seeds, `segment`, the named maps (`range`, `range2`, `rangex`, `add`, `sub`, `mul`, `div`, `round`, `floor`, scales, voice patches), arithmetic, `fast`, `slow`, `rev`, `every` (the transformed pattern it stored), `cat`, `seq`, `timecat`, `stack`, `arrange`, `euclid`, `pure`, `n`, and the controls.

**What cannot cross a thread.** A `Custom` node (a Rust closure or `Query`: `from_fn`, `fmap_with`, `signal_from_fn`, and so a `Pattern<f64>` given to a control, which is mapped with a closure on the way in) and a `Foreign` node (a callback that lives in the host, such as a JavaScript function: `signal(fn)`, `fmap(fn)`, `new Pattern(query)`) are refused with an error that names them. A tree holding either stays on the thread that built it. Everything else crosses.

## The thread check

`crates/undertone-pattern/tests/serialize.rs`: each tree is serialised, the text is moved to a new `std::thread`, the tree is rebuilt there, and both copies answer 1,000 queries of varied spans (denominators up to 12, negative time, up to five cycles long) and 500 `sample_at` points. Haps and values are compared as their `Debug` text (every `f64` printed exactly), and the rebuilt tree must hash and write the same.

- **Corpus `signals` programs (layers 1 and 2):** 119 trees, about 669,000 haps and 59,500 samples compared, no difference, none refused.
- **Every other corpus program:** 573 trees round-tripped with 20 windows each, no difference, none refused.
- **Hand-built trees:** 43 trees over every signal, seed, and combinator, plus controls, scales, banks, pan paths, `jux`, and rich values: about 116,000 haps and 21,500 samples, no difference.
- **Property (proptest, 10,000 cases, and 1,000 while iterating):** random programs of depth 2 serialise, rebuild, write the same text, hash the same, and answer the same.

## What this enables

The worklet (RF-29) can query patterns off the main thread when the tree has no foreign leaf: the main thread builds the pattern, sends the text, and the worklet (or a worker) rebuilds the tree and queries it there, with nothing shared but a string. The worklet backend refuses a pattern whose `serialize` fails, with the error's message as the diagnostic. [R4](R4.md) found the worklet should carry no text parser; the serialised form needs only a small reader (the module is about 890 lines before its tests, writer and reader both) with no mini-notation parser and no scale parser (a scale is rebuilt by table lookup); its size in the worklet is for RF-29 to measure.

## The benchmark

`cargo run --release -p undertone-engine --example signal_bench` against `src/signal.bench.ts`, both on this machine (AMD Ryzen 7 7700X, Linux 7.2.9, bun 1.4.4, rustc 1.98.0). `s("hh*16")` with three controls through 1,000 windows of a twentieth of a cycle (800 voices), mean of 200 runs after 10 warm-up runs, whole tick (query, onset filter, gate length, `resolve_params` or `resolveParams`). The TypeScript figures come from a small `bun` script that calls the same `collectOnsets` the bench calls, not from `vitest bench` (that needs `bun install`; the bench file's own figures in the guide came from Node).

| Workload              | TypeScript (ms) | Rust (ms) | Rust query and onsets only (ms) | TypeScript query and onsets only (ms) |
| --------------------- | --------------: | --------: | ------------------------------: | ------------------------------------: |
| no controls           |            0.87 |      0.57 |                            0.26 |                                  0.75 |
| three number controls |            2.16 |      1.72 |                            1.27 |                                  1.93 |
| three string controls |            21.5 |      4.65 |                            4.17 |                                  21.6 |
| three signal controls |            2.41 |      1.92 |                            1.45 |                                  2.22 |

The acceptance, at most the TypeScript's figure, holds in all four rows. The signal row is only 1.25 times faster than the TypeScript, because the control merge clones a map for each hap; the string row is 4.6 times faster. Neither figure is a CI gate. The benchmark was not run in a browser; the numbers are one native machine's.
