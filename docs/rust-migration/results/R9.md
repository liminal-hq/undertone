# R9: maths determinism

Spike R9 (RF-08) on `chore/spike-r9-maths-determinism`, based on `origin/main` at `36943dc`. The question: does the engine use the C library natively and `libm` in WebAssembly, or `libm` everywhere?

## Verdict

**Pass with conditions.** Use the platform C library natively and the `libm` crate in WebAssembly. The fail fallback (`libm` everywhere) is not needed.

- **Native against the reference:** on this Linux and glibc machine the Rust standard library's maths equals JavaScriptCore's bit for bit on 1,307,437 of 1,307,439 swept values, and at nine significant digits on all of them. The two others are one unit of the last place apart (`2 ** -0.5`).
- **WebAssembly against native:** the `libm` back-end differs from glibc by at most one unit of the last place on `sin`, `cos`, `acos`, `exp`, `ln`, and `pow` (about 3 percent of values differ in the last bit). Every number the corpus records today (the 14 pan-law voices, the pan-law path, the autopan scale, and the autopan wave tables) is identical at nine digits with both back-ends. The RMS difference of every swept set is at most 4.0e-16, far under the 1e-6 limit, except `exp`, whose values reach 4.8e8 (its relative difference is 2.2e-16 like the others).
- **The conditions:** (1) the layer 3 comparison of wave coefficients in the WebAssembly runs needs an absolute floor of 1e-15, because 179 of the 390 coefficients of the three shaped waves (`halfsine`, `abssine`, `pulsesine`) are numerical zeros of at most 2.4e-16 that the two back-ends round differently, and the corpus will record them when the `voices` group lands; (2) `libm` is pinned exactly and the WebAssembly build always sets the `libm` feature, because the standard library's own maths on `wasm32-unknown-unknown` differs from the crate in 2,456 values of the sweep; (3) byte-for-byte layer 3 comparison with the C library holds on Linux with glibc only, so it runs in Linux CI, and other operating systems are untested.

Other measurements:

- **The `libm` WebAssembly build** is bit-identical to the native `libm` build on all 1,307,439 values, so WebAssembly adds no difference of its own.
- **Divergence test:** `math::tests::divergence` (with the `libm` feature) fails if the back-ends differ by more than four units of the last place, or by more than 1e-15 absolute, over sweeps of `sin`, `cos`, `exp`, `ln`, `acos`, the pan-law and pitch `pow`, and the shaped wave tables. The measured difference is at most one unit of the last place, so the stated tolerance has margin.
- **Side check, V8:** Node's `Math` functions differ from JavaScriptCore's in 57,352 bits of the first 1,291,590 values (the raw functions, not the tables), at most 2.2e-16 relative, and in none of them at nine digits. So the TypeScript reference itself is not bit-exact across JavaScript engines; only the glibc maths matches the corpus's engine exactly.

## What failed and why

Nothing failed outright. Two findings:

- **The `libm` crate does not reproduce glibc at the last bit.** Its `sin`, `cos`, `exp`, `ln`, and `pow` are within one unit of the last place of glibc's, but not equal, about 3 to 10 percent of the time. That is invisible at nine digits for every value except the numerical zeros of a wave table, where a coefficient such as `-4.81e-17` (JavaScriptCore) becomes `-3.43e-17` (`libm`). Those coefficients have no audible effect (the largest is 2.4e-16 of a coefficient of order one), but a byte-for-byte comparison sees them. The recorded autopan waves also contain such zeros (for example `6.12323426e-17`) and match with both back-ends, so this is a property of particular values, not of the module.
- **JavaScriptCore special-cases `2 ** -0.5`.** It gives `0.7071067811865475`; glibc and `libm` give `0.7071067811865476`, which is the correctly rounded value. The difference of one unit of the last place is under the nine-digit rounding of every recorded number it can reach (pitches multiply it by a frequency), so I did not emulate it.

The standard library's maths on `wasm32-unknown-unknown` is a compiler-provided port of `libm` and is not the same code as the crate (2,456 values differ), so a WebAssembly build without the feature would give a third set of last-bit differences. It builds, but the engine must not rely on it.

## What it changes

- **[CONFORMANCE.md](../CONFORMANCE.md):** the tolerance table gains the engine-maths decision (written in this change).
- **Design:** `undertone-engine` takes its maths from `math::Active`: the C library by default, `libm` with the `libm` feature. The WebAssembly bridge crate (RF-26) must enable the feature for `wasm32` and pin `libm` to an exact version. The kept module is `crates/undertone-engine/src/math.rs`, `math/waves.rs`, and `math/gains.rs`; the next work packages build on it (RF-18 for gains, the voices and channels groups for the wave tables), and the sweep example stays as the way to re-measure.
- **Layer 3 runners:** the Rust runner (native, Linux) compares byte for byte. The package's WebAssembly runner (RF-27) compares wave coefficients and gains at nine digits with an absolute floor of 1e-15 (a value within 1e-15 of the recorded one passes), and everything else byte for byte. The corpus is not edited.
- **Layer 4:** compares with tolerances, as already planned, so the last-bit differences between native and WebAssembly do not matter there. "Rust native against Rust WASM" in the tolerance table is "within 1e-6 RMS" (measured 4.0e-16 at most on the maths, relative differences 2.2e-16).
- **Not changed:** the pass criteria, [ARCHITECTURE.md](../ARCHITECTURE.md), and [API-MAPPING.md](../API-MAPPING.md).

## What was not verified

- **Nothing was listened to.** No audio was rendered; the "RMS" figures are RMS differences of maths outputs (sweeps and wave tables), a stand-in for the 1e-6 render RMS of the pass criterion, which needs the engine's DSP and layer 4 (RF-20).
- **Other C libraries:** glibc 2.44 only. macOS, Windows (MSVC), musl, and other glibc versions are untested; their `sin`, `exp`, and `pow` may differ at the last bit, so native equality with the corpus is a Linux claim. Whether the machine that recorded the corpus used the same glibc is not known; the corpus numbers computed here matched.
- **Other engines and CPUs:** WebAssembly was run under V8 (Node 22) only, on x86-64. I did not run `libm` under other WebAssembly engines or on Arm.
- **Not covered by the corpus yet:** shaped waves, the reverb impulse response (its `exp` envelope is swept, but the recorded buffer summaries also depend on the seeded random source), pitch frequencies, and the master-bus `pow` curves. The sweep covers the functions and arguments, not those recorded values.
- **The JavaScript engines' own differences** (JavaScriptCore against V8) were measured on raw functions only, not on the tables.
