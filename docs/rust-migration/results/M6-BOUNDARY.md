# M6 boundary: how the Rust API crosses into JavaScript

The conventions for every export of `crates/undertone-wasm` (RF-24, both pull requests) and for the TypeScript bridge that wraps it (`packages/undertone`, RF-25). Part 1 of RF-24 wrote this file before the bulk of its code and keeps it current; part 2 (the controls, chords, scales, drift, instruments, samples, engine, render, WAV, score, and scheduler) follows it, and changes it in the same commit when a rule has to move.

Every decision below names the measurement or the earlier result behind it. "Measured" figures come from this machine (AMD Ryzen 7 7700X, Linux 7.2.9), Node 22.21.1, Bun 1.4.4, Rust 1.98.0, `wasm-bindgen` 0.2.125, binaryen 132, unless a row says otherwise. KB is 1,000 bytes, as in R4. Nothing here makes sound, and nothing was listened to.

## 1. Handles

- **One exported struct per Rust type that JavaScript holds.** `WasmPattern` wraps `Pattern<Value>`, `PatternList` is the list builder, and `WasmRandom` is `seededRandom`'s generator; part 2 adds `WasmEngine`, `WasmPlayer`, and so on, each named `Wasm` plus the Rust type. The JavaScript class names are the Rust ones, never the bridge's public names, so the generated glue (`undertone_wasm.js`) and the wrapper (`packages/undertone/src/`) cannot be confused: the wrapper's `Pattern` holds a `WasmPattern` in a private field.
- **Every method returns a new handle,** as every TypeScript method returns a new `Pattern`. A method never mutates its receiver; the receiver is always borrowed (`&self`), so a handle can be used again after any call.
- **Freeing:** `wasm-bindgen --weak-refs` registers every handle with a `FinalizationRegistry`, so the garbage collector frees it eventually (R2: late, because the collector cannot see WebAssembly memory). `free()` frees it at once. **The glue's own `free()` is not idempotent:** a second call throws `Error: null pointer passed to rust` (measured; the glue zeroes the pointer and then passes 0 to Rust). So the wrapper's `free()` and `[Symbol.dispose]()` (RF-25) keep a flag and call the glue's `free()` once. A method called on a freed handle throws the same `null pointer passed to rust`, which the wrapper may turn into "this pattern was freed".
- **Lists are built with borrowing `push` calls, never as an array of handles.** wasm-bindgen moves an exported struct out of a JavaScript array (`Vec<WasmPattern>`) and nulls the JavaScript object (R5). So `seq`, `cat`, `stack`, `timecat`, and `arrange` take a `PatternList`: `new PatternList()`, then `push(handle)` or `pushWeighted(weight, handle)` per item (each borrows and clones the tree's `Arc`), then `seq(list)` and the others borrow the list. The wrapper frees the list straight after the call. `choose(...values)` takes plain values, not handles, so it takes an array.
- **No generics cross.** Every export is monomorphic (`Pattern<Value>`); `Pattern<f64>` and `Pattern<bool>` never cross.

## 2. JavaScript functions

There are three kinds, and each has one rule.

- **Called once, at construction:** `every(n, fn)`, `jux(fn)`, and the leaf rule of `mini(source, leaf)`. Rust runs the function during the call that builds the pattern, and the tree keeps only the result (the closure-at-construction rule of the pattern crate). For `every` and `jux` the wrapper passes a **thunk** that takes no argument, calls the user's function with the wrapper's own receiver, and returns a fresh clone of the handle it got back (`() => fn(this).handle.clone()`), so `fn` sees the same `Pattern` object as in `pattern.ts` and nothing the user holds is nulled when Rust takes the clone. Rust calls the thunk from inside the pattern crate's own `every` or `jux`, so the order of checks is the reference's: `every(0, fn)` fails with the cycle-count message before `fn` runs (measured: the function is not called). An exception thrown by the user's function is rethrown unchanged (same object, same class) after the pattern crate returns; a thunk that returns something else than a handle fails with `a transform's thunk must return a pattern handle`.
- **Called during every query: the foreign leaves.** `new Pattern(query, sampler?)` (`fromQuery`), `fmap(fn)`, and `signal(fn)` become a `Node::Foreign` leaf. The host is `JsLeaf`, one per leaf, holding only its `ForeignId` (a `u32`), so it is `Send + Sync` without `unsafe`: the JavaScript functions themselves live in a thread-local table in the bridge (`foreign.rs`), keyed by the id. When the last tree holding the leaf is dropped, `JsLeaf`'s `Drop` removes the table entry, which releases the functions (measured: 1,000 leaves made and freed leave the table as it was; a leaf inside a pattern that is still alive stays). On any other thread the table is empty, so the leaf is silence there, and `Pattern::serialize` refuses the tree with an error naming the foreign node (RF-16), which is the diagnostic the worklet backend reports (D-40, B4 and B5).
  - `fromQuery(query, sampler?)`: Rust calls `query(beginN, beginD, endN, endD)`; the wrapper builds the `TimeSpan`, calls the user's query, and returns the haps in the encoding of section 3 (`[Float64Array, values]` or `[Float64Array, values, big]`). The sampler is `sample(n, d)` returning the value or `undefined`, and it is carried through transforms (measured: `clock.fast(2)` keeps it; R5 lost about 20 tests without it). A time beyond the safe range reaches either function as `NaN` and its `n/d` text in place of the two numbers. A result of the wrong shape fails the query with `a JavaScript query must return [Float64Array, values] or [Float64Array, values, big]`.
  - `fmap(map)`: the leaf holds the child pattern and one function. Rust queries the child, then calls the function **once per query** with the array of the haps' values and expects the array of mapped values back (the wrapper passes `(values) => values.map(fn)`), so a query crosses the boundary once, not once per hap (measured: one call for an eight-hap query). A child with a sampler keeps it: a sample calls the same function with a one-element array.
  - `signal(fn)`: Rust calls `fn(t)` with the cycle time as a number, as `continuous` does in `signal.ts` (a query returns one hap with no whole and the value at the span's begin; the sampler is `fn(t)`).
  - **A function that throws during a query:** the leaf records the exception and answers nothing; when the query returns to the export, the export rethrows the first recorded exception unchanged. So an exception in a user's query or map reaches the caller of `.query` or `.sampleAt`, as in the reference (measured: the same `TypeError` object). A callback may itself build or query patterns: the table is never borrowed while a callback runs, and a failure recorded by an inner query stays with the inner query.
- **The mini-notation leaf** runs once per word; its exception becomes the parse error with its message at the word's position, as `mini.ts` reports it (`error instanceof Error ? error.message : String(error)`).
- **Never stored as a closure in Rust.** No export takes a JavaScript function into a `Custom` node; a `Custom` node is Rust-only.

## 3. Query results

**The flat encoding, with value interning,** chosen by measurement:

- `query(beginN, beginD, endN, endD)` returns `[times, values, big]`: `times` is a `Float64Array` of nine numbers per hap, in the tree's order (part begin n, d; part end n, d; whole begin n, d; whole end n, d; the value's index); `values` is an array of the distinct values; `big` is an array of fraction texts, or `undefined` when there are none.
- **A hap with no whole** has all four whole slots 0 (a denominator is never 0).
- **Interning:** equal values among the last 16 distinct ones cross once (numbers compared by their bits, so `-0` and `0` stay apart and a `NaN` matches the same `NaN`). So haps with equal values share one JavaScript object, as the haps of one mini-notation leaf share one object in the reference. Every query gives fresh objects (B9).

The measurement: one query of 1,000 haps (cycles 0 to 125 of an eight-step pattern), median of 300 after 50 warm-up runs, "with `Hap` objects" including the wrapper building `{ whole, part, value }` with the reference's `Fraction`. The objects encoding was `serde-wasm-bindgen` over plain `{ whole?, part, value }` objects with `{ n, d }` fractions, built for this measurement and then removed.

| Values (1,000 haps)                 | Runtime | Query alone | Flat, interned: crossing / with `Hap`s | Flat, not interned: with `Hap`s | Objects: crossing / with `Hap`s |
| ----------------------------------- | ------- | ----------: | -------------------------------------: | ------------------------------: | ------------------------------: |
| Strings (8 distinct)                | Node 22 |      215 µs |                           303 / 412 µs |                          477 µs |                1,046 / 1,181 µs |
| Voice maps of 3 fields (8 distinct) | Node 22 |      368 µs |                           585 / 699 µs |                        1,269 µs |                1,854 / 1,978 µs |
| Numbers (a signal's `segment(8)`)   | Node 22 |      193 µs |                           290 / 410 µs |                          412 µs |                  968 / 1,088 µs |
| Strings                             | Bun 1.4 |      170 µs |                           219 / 390 µs |                          444 µs |                    722 / 892 µs |
| Voice maps                          | Bun 1.4 |      265 µs |                           403 / 575 µs |                          987 µs |                1,317 / 1,507 µs |
| Numbers                             | Bun 1.4 |      166 µs |                           212 / 376 µs |                          379 µs |                    665 / 832 µs |

The flat encoding is 2.2 to 2.9 times faster than the objects in every case, and interning halves the maps' time again, for 342 bytes of module. The Rust query itself is 0.17 to 0.37 µs a hap here, against R2's 2 µs (RF-13's fast path). Both encodings gave the same haps.

Rules that go with it:

- **Fractions cross as two numbers when both fit a JavaScript safe integer** (|x| ≤ 2^53 − 1), which is every fraction of every corpus case. A fraction that does not fit (B3, D-13: Rust's `i128` goes beyond 2^53) crosses as its exact text `n/d`: its numerator slot is `NaN` and its denominator slot is the index of the text in `big`. A text, not a `BigInt`, because it costs no `BigInt` glue and the wrapper parses it with `BigInt(...)` only in that rare case; a numerator is never `NaN` otherwise, so the marker is unambiguous. The wrapper's `Fraction` must be able to hold such a value (RF-25); `fractionOp` and `fractionFromNumber` give it exact arithmetic (section 10).
- **Spans go in the same way:** `query(beginN, beginD, endN, endD)` takes four numbers, each an integer within the safe range and a denominator that is not 0, or it throws `a time must be two safe integers with a denominator that is not 0, got 1/0`; `queryRatio(begin, end)` takes two texts (`"1/3"`, `"4"`) for the tail. `sampleAt(n, d)` and `sampleAtRatio(text)` likewise.
- **Values** (`Value`: number, string, boolean, map, list, `undefined`) leave Rust through `serde-wasm-bindgen` (`Serializer::new().serialize_maps_as_objects(true)`: maps become plain objects; not `json_compatible()`, which would write `undefined` as `null`), and come in through a hand-written conversion (`convert.rs`), not `serde-wasm-bindgen`'s deserialiser, because its `deserialize_any` reads every safe integer as an `i64` and so turns `-0` into `0` (checked in its source, 0.6.5, `de.rs`).
  - **Numbers** cross as JavaScript numbers in both directions, bit for bit: `NaN`, `Infinity`, `-Infinity`, and `-0` keep their identity (measured, nested inside maps and lists too).
  - **`undefined`** is `Value::Undefined` both ways; a map field set to `undefined` is a key present with the value `undefined`, as `{ ...defaults, soundType: undefined }` makes it.
  - **Map keys come back sorted** (`Value::Map` is a `BTreeMap`, as the corpus sorts them), where a reference object keeps its insertion order. Nothing in the suite or the corpus depends on the order.
  - **`null`, class instances, functions, symbols, and `BigInt`s cannot be held:** putting one into a pattern (`pure(null)`, `choose(new Fraction(1, 2))`, a leaf rule or a map returning one) throws `a pattern value must be a number, a string, a boolean, undefined, an array, or a plain object, got <String(value)>`. Plain objects are those whose prototype is `Object.prototype` or `null`. A value nested more than 64 levels deep (a cycle, say) is refused too. This is narrower than the reference, which holds any JavaScript value; see section 11.
- **`hasOnset(hap)`** stays a JavaScript function of the wrapper's `Hap` (`whole.begin.eq(part.begin)`): it needs no export.

## 4. Errors and panics

- **A Rust error becomes a thrown JavaScript `Error` whose `message` is the Rust message word for word** (`js_sys::Error::new(message)`), so the corpus's recorded messages compare equal (B10, D-40). The class stays `Error`: no subclass, no `name` change, no extra fields (measured: `error.constructor === Error`).
- **Mini-notation messages keep the source's own UTF-16 code units.** A Rust string cannot hold a lone surrogate half, so the pattern crate's parser reports an emoji at position 2 as `unexpected "\u{fffd}"` where the reference says `unexpected "\ud83d"`. The `mini` export takes the source as a `JsString` and rebuilds the message from it (`mini_message` in `build.rs`): the quoted source as given, and the code unit at the reported position. That made the 15 `mini-err-astral` corpus cases equal. Part 2 should reuse it for every export that parses text through mini-notation (`note`, `sound`, `s`, `n`, `chord`, and the controls' string inputs).
- **A JavaScript exception from a user's function passes through unchanged** (section 2), so its class and fields survive.
- **Validation that the reference does in JavaScript stays in JavaScript** (R5): `add() needs a number or a pattern of numbers` is the wrapper's, because only the wrapper can tell a `Pattern` from anything else. The export takes the two shapes as two methods (`arith(op, number)` and `arithPattern(op, handle)`).
- **No panic is meant to cross the boundary,** and the exports are written so that none can on any input JavaScript gives them: numbers are checked before they become fractions, fraction texts are parsed with `i128::MIN` refused, the exact helpers bound each part below 2^63, the foreign table is borrowed with `try_borrow` and never across a callback, and nothing calls `unwrap` on a value JavaScript chose.
- **If one does happen, the instance is dead.** The module is built with `panic = "abort"` (R4's profile; it is also the only panic strategy `wasm32-unknown-unknown` supports on stable Rust), so a panic is a WebAssembly trap: the call throws `RuntimeError: unreachable` (Node; Bun says `Unreachable code should not be executed`) and no Rust destructor runs. The linear memory can be left mid-update (a `RefCell` borrowed, a list half built), so the wrapper must treat that instance as unusable; the remedy is a new instance (a page reload, or a fresh `./init`). There is no panic hook: `console_error_panic_hook` would add an import and the formatting of the panic message for a case that is a bug by definition. **One way to panic is known and kept on record by the smoke test:** the pattern crate's `Fraction` panics on `i128` overflow (`Fraction overflow`), so `pure(1).fast(2 ** 53).fast(2 ** 53).fast(2 ** 53)` traps when queried. In 0.3 such a pattern silently lost precision instead. A checked query in the pattern crate (returning an error) would close it; it is not part of RF-24.

## 5. Naming

- **JavaScript names are camelCase through `js_name`, matching `src/index.ts`** wherever an export carries a reference name: `midiToFrequency`, `noteToMidi`, `noteToFrequency`, `seededRandom`, `brandBy`, `sampleAt`, `hasSampler`. A name that is already one word keeps it (`fast`, `rev`, `euclid`, `pure`, `seq`).
- **An export the wrapper uses but the reference does not have** is named for what it does: `fromQuery`, `queryRatio`, `sampleAtRatio`, `arithPattern`, `pushWeighted`, `signalNamed`, `controlTable`, `fractionOp`, `fractionFromNumber`, `undertoneVersion`, and the diagnostics `liveHandles`, `liveForeignFunctions`, `memoryBytes`.
- **The signals are one export, `signalNamed(name)`,** over the pattern crate's `signal::by_name` (the names are the reference's). The wrapper builds its constants (`export const sine = ...`) from it once at load. Twenty separate exports would cost glue for no gain.
- **Rust names** follow the crate's: `WasmPattern::every`, `WasmRandom::next_value` (`next` in JavaScript, because Clippy reserves `next` for `Iterator`).

## 6. The controls table

The wrapper (RF-25) generates its control methods from the table instead of writing 53 by hand, and the bridge has one dispatcher.

- **`controlTable()`** (part 1) returns `undertone_pattern::CONTROLS` as an array of plain `ControlRow` objects: `jsName`, `rustName`, `fields` (the `VoiceParams` JSON names), `arg` (`patternable`, `patternableWithTime`, `integer`, `number`, `choice`, `text`, `numberList`, `path`), `scalarOnly`, `messageName`, `choices`, `range`, and `summary`. The wrapper reads it once at load and installs one method per row on `Pattern.prototype`; the TypeScript declarations for those methods stay hand-written (the API report checks them, RF-06), and a test in RF-25 checks the generated set against them. Cost: 2.5 KB after Brotli (measured by building without it), mostly the table's own text.
- **The dispatchers (part 2a).** The wrapper picks one by the row's `arg`:
  - every row but four: `.control(jsName, value)` with a number, a mini-notation string, or any other value (read as `String(value)`, so a plain-value control reports it as the reference does: `cut() must be a non-negative integer, got true`), or `.controlPattern(jsName, handle)` with a pattern, the two shapes because a handle cannot be read out of an untyped value. `undefined` or `null` for a patternable control is refused with `gain() needs a number, a mini-notation string, or a pattern, got undefined` (the reference throws a `TypeError` from inside its parser there). A scalar-only control given a pattern is refused in Rust with the reference's `takes a plain value` message, so the wrapper needs no list of them. Both run the pattern crate's `Pattern::control`, so every check and message is the crate's;
  - `patternableWithTime` (`panslide`): `.panslide(from, seconds)` and `.panslidePattern(handle, seconds)`;
  - `numberList` (`pitchsteps`, `channels`) and `path` (`panpath`): `.pitchsteps(semitones, rate)`, `.channels(gains)`, `.panpath(path, rate)`, which take the JavaScript array. The wrapper checks `instanceof Pattern` on the array (and on `panslide`'s `seconds`) first and throws the `takes a plain value` message itself, as `rejectPattern` does, because Rust cannot see a wrapper `Pattern` inside an untyped value;
  - `sound`, `s`, `bank` (`text`) have their own methods (`.sound`, `.s`, `.bank`, group 7), though `control` takes them too.
  - The other plain-value controls (`orbit`, `cut`, `panlaw`, `surround`, `fmenv`, `fmwave`, `autopanshape`) go through `control(name, value)` and have no export each: the messages are the same and the glue stays smaller. This narrows the brief's "own exports" list; RF-25 calls them through the dispatcher.
- **Why a table and a dispatcher, not 53 exports:** R4 measured both: the 53 named exports cost 614 bytes more after Brotli in the module and 33 KB more of unminified glue (606 bytes after Brotli), and the table cannot drift from the generated methods. The real dispatchers with the four list methods and `voice` cost 4.8 KB after Brotli (section 9).
- **`CONTROLS` is now a `static`** (it was a `const` slice, so the module held three copies of its rows and strings: 22 KB raw, 2.5 KB after Brotli, measured).

## 7. Typings

- **Hand-written `.d.ts` for the handle classes** and for everything the wrapper alone sees (D-11): the glue already declares every export (`undertone_wasm.d.ts`, from the Rust signatures), and the wrapper's public types are the 0.4.0 ones, written by hand and checked by the API report.
- **`ts-rs` for the data types that cross as plain objects** (D-11). ts-rs 12.0.1 (MIT; `cargo deny` passes) is a **dev-dependency only**: the types derive `TS` under `#[cfg(test)]`, a unit test renders each declaration and compares it with the committed file under `crates/undertone-wasm/bindings/` (`UNDERTONE_UPDATE_BINDINGS=1 cargo test -p undertone-wasm` rewrites them), and RF-25 copies or imports them. So ts-rs adds nothing to the module. Part 1's types are `ControlRow` and `ControlArg`; part 2 adds `VoiceParams`, `ScoreEvent`, `RenderOptions`, `PlayOptions`, and the other option bags. `tsify` was not taken: it would put its derive and `wasm-bindgen` attributes into the build of the module itself. Prettier and ESLint skip the generated files.
- **The value type** (`Value`) is not generated: in TypeScript it is the reference's `unknown` (a hap's value) or `ControlPatch`, already declared.
- **`VoiceParams` and `ControlPatch` (part 2a) cross as plain values, not through a `serde` derive,** so no ts-rs declaration is generated for them: `resolveParams(patch)` is the reference's `{ ...DEFAULT_PARAMS, ...patch }` plus the sample rule, done on the `Value` (`data.rs`), so it keeps a key that is not a field (`degree`, `chord`: the corpus records them) and a value of an unexpected kind exactly as the spread does, and gives the optional defaults (`pitch`, `sampleName`, `sampleBank`, `filterCutoff`, `hpfCutoff`, `phaserRate`, `roomLevel`, `delayLevel`, `orbit`) as `undefined`, as `DEFAULT_PARAMS` lists them. Going through the engine's typed `VoiceParams` would drop those keys and values. The default numbers are read from `VoiceParams::empty()`, and a unit test checks that the engine resolves them back to its own defaults and that every key is a field of `conformance/api/voice-params.json` (the field names are already checked against the same file by the engine's serde test). The public declarations stay the 0.4.0 hand-written ones (`src/types.ts`), checked by the API report; RF-25 copies them. **For part 2b:** `playParams(ctx, voices)` can take each voice the same way (`from_js`, then the engine's `resolve_params`, which is the identity on a complete `VoiceParams` map), so the module may never need `serde` for `VoiceParams` (R4 measured 7.2 KB for it).

## 8. Testing and diagnostics hooks (part 2 and RF-25)

D-28 ships `@liminal-hq/undertone/testing` with `resetWarnings`, `seedContext`, and `playVoice`/`playVoices`. What the Rust side must give it, none of which exists in part 1:

- **Warnings (part 2a, `warnings.rs`).** The reference's `warnOnce(key, message)` prints with `console.warn` once per key per process, and `resetWarnings()` clears the set. The bridge keeps **one once-only set of keys per instance** and **prints a new warning with `console.warn` itself**, through a `wasm-bindgen` import of `console.warn` that the glue looks up at each call (`console.warn(getStringFromWasm0(...))`, so `vi.spyOn(console, 'warn')` sees every warning). The wrapper has nothing to consume or forward; its `./testing` `resetWarnings` calls the module's **`resetWarnings()`** (and clears any warnings the wrapper keeps itself). Chosen over a `takeWarnings()` queue because the wrapper would have to drain it after every call that can query (and in a `finally`), and over a registered callback because a callback that only calls `console.warn` adds nothing; all three cost about the same (the whole of `warnings.rs` is 2.4 KB of function bytes, mostly the `BTreeSet<String>`). Two instances (`.` and `./init`) keep two sets, as two separate programs would.
  - **Controls:** the pattern crate's sanitising now reports each value it deals with as a `ControlWarning` (the reference's `signal-nan-<name>` and `signal-range-<name>` keys, `<name>` being the message name, so `fmi` warns as `fm`, and the messages word for word, with `String(value)` for a string, a boolean, a list, or an object a pattern gave) to `controls::collect_warnings(run)`, a `std`-only, opt-in, thread-local collector that keeps each key once per call; outside a call nothing is formatted. `query`, `queryRatio`, `sampleAt`, and `sampleAtRatio` run inside it and print the new keys when the query returns (before an exception from a foreign leaf is rethrown). A rest or `undefined` is silent, as in the reference.
  - **The engine (part 2b):** the engine keeps its `Warning`s per `Engine` (`undertone-engine/src/warn.rs`, with keys); the bridge should pass each new one to `warnings::warn_once(key, message)`, so one set covers the controls and every engine, as one set covers the reference's.
- **`seedContext(ctx, seed)`** seeds the noise and impulse-response randomness of one context. The bridge needs an export on its engine that sets that seed (the engine's random sources are `undertone-engine/src/random.rs`).
- **`playVoice(ctx, params, options)` and `playVoices`** become calls of `playParams` with a resolved `VoiceParams` (R5); the Rust side needs `Engine::play_params` exported with `VoiceParams` crossing as a plain object.
- **Part 1 already has** `liveHandles()` (pattern handles made minus dropped), `liveForeignFunctions()` (functions held by foreign leaves), and `memoryBytes()` (the linear memory's size), used by the smoke test and available to RF-25's million-handle test. They are not public API.

## 9. Build, size, and CI

- **Profile `wasm`** in the root `Cargo.toml` inherits `release` and sets `opt-level = "z"`, `lto = "fat"`, `codegen-units = 1`, `panic = "abort"`, and `strip = true`: R4's profile (R4 measured `"s"` 5% larger after Brotli than `"z"`). The `release` profile the native crates use is unchanged.
- **Lints:** the workspace table, `unsafe_code = "forbid"` included. wasm-bindgen 0.2.125's macro output does not trip `forbid` (checked with exported structs, `Result<_, JsValue>`, a `Vec` of handles, and an `extern` import), so the crate needs no `deny` table like `undertone-sched`'s, and `scripts/check-layering.sh`'s unsafe check needed no change.
- **`scripts/build-wasm.sh`** checks that `wasm-bindgen --version` equals the crate's pin (and prints `cargo install wasm-bindgen-cli --version =0.2.125 --locked` if not), builds `--target wasm32-unknown-unknown --profile wasm -p undertone-wasm`, runs `wasm-bindgen --target web --weak-refs` into `packages/undertone/wasm/`, runs `wasm-opt -Oz` with the WebAssembly features rustc 1.98 emits (bulk memory and its `-opt` form, `call_indirect` overlong, multivalue, mutable globals, non-trapping float-to-int, reference types, sign extension), and prints the raw and Brotli sizes.
- **Not `wasm-opt -all`:** binaryen 132's `-all` turns on the compact import section, which Node 22 and Bun 1.4 refuse to compile (`unknown import kind 0x7f`); R4 never ran its modules, so it did not see this. The explicit list loads in both and, against `-all` with only the compact imports turned off, is 2.2 KB larger raw and 0.5 KB smaller after Brotli (measured on the module before the two cuts below).
- **`wasm-opt` barely changes the Brotli size:** on the same build it took the module from 339 KB to 299 KB raw (12%) but from 105.1 KB to 106.3 KB after Brotli (+1%), where R4 measured −1 to −2%. It stays, for the raw size (parse and compile time), as D-22 and R4 asked.
- **`scripts/wasm-opt/`** pins `binaryen` 132.0.0 in its own `package.json` and `bun.lock` (which carries the package's sha512 integrity), installed with `bun install --frozen-lockfile` on first use and run under Bun, so the root `package.json` gains no dependency.
- **`scripts/check-wasm-size.ts`** (Bun) fails when the control module is over 150 KB after Brotli 11 and warns over 90% (D-07), and writes the figures to the job summary. Its Brotli figure matched the `brotli -q 11` tool R4 used within a byte.
- **CI: the `wasm-bridge` job** (D-41) runs on `ci-rust` at the same digest as the other Rust jobs and installs the wasm32 target, the wasm-bindgen CLI (the prebuilt musl release binary, checked against its pinned SHA-256: 0.5 s, where `cargo install` from source took 35 s with four jobs and a warm registry on this machine), and Bun 1.4.4 (the release zip, checked the same way). Then Clippy for wasm32, the build, the size check, the smoke test, and corpus layers 1 and 2 (layer 2 since part 2a). No cache action: the repository uses none. The same steps in the pinned image under Docker, four CPUs, cold Cargo registry: 26 s (target 1.4 s, CLI 0.4 s, Bun 1.2 s, Clippy 8.2 s, build 14.1 s, size 0.4 s, smoke 0.3 s, layer 1 0.8 s), before the runner's image pull and checkout. The real job time on a runner is not measured (nothing is pushed).

### The module's size

## 11. Decisions for review

- **`null` and non-plain objects cannot be a pattern's value** (section 3). The reference holds any JavaScript value (`pure(null)`, `pure(new Fraction(1, 2))`, a class instance from a leaf rule). Holding them would need an opaque value in the pattern crate (a `Value::Foreign(id)` resolved by the bridge, as the foreign leaves are), which changes `undertone-pattern`. The default taken here: refuse them with one clear message, and list it as a break under D-06 (it is not in B1 to B10). The suite and the corpus do not use such values.
- **Map keys come back sorted** (section 3), not in the reference's insertion order. Inherent in `Value::Map`; nothing depends on it.
- **Equal values in one query share one object** (section 3, interning). Closer to the reference than one object per hap, but not identical: two separate leaves with equal words share in the bridge and do not in the reference. Only a caller that mutates a hap's value could tell.
- **`wasm-opt` runs without `-all`** (section 9), against R4's and D-22's wording, because `-all` makes a module Node and Bun cannot load.
- **`free()` twice throws in the glue** (section 1); the wrapper must guard it.
- **A panic leaves the instance unusable** and one is reachable through `i128` overflow (section 4). A checked query in the pattern crate is the fix; not done here.
- **`CONTROLS` changed from a `const` to a `static`** in `undertone-pattern` (section 6), the one change outside `undertone-wasm`, for 2.5 KB.
- **`describe()` was dropped** from the module (3.6 KB); it can come back behind a feature for a debugging build.
- **Part 2's room is about 50 KB after Brotli** (section 9), tight against R4's extrapolation.
- **Part 2a used 26.8 KB of it** (section 9): 7.9 KB is left to the warning and 22.9 KB to the budget, so part 2b cannot fit the engine, booking, rendering, and the scheduler in the control module as one module. Which groups go to a second, lazily loaded module (or behind features) needs a decision before part 2b; the measured candidates are in section 9.
- **The pattern crate reports control warnings** through `controls::collect_warnings` (`std` only, opt-in), the second change outside `undertone-wasm` (section 8); and the mini-notation parser borrows its leaf as `&dyn Fn` (−30 KB raw), with `tests/closures.rs` allowing that one borrowed closure.
- **`resolveParams` works on the value, not the typed `VoiceParams`** (section 7), so it keeps the reference's extra keys; no ts-rs declaration of `VoiceParams` or `ControlPatch` is generated, and the public declarations stay hand-written.
- **The plain-value controls have no export each** (section 6): `orbit`, `cut`, `panlaw`, `surround`, `fmenv`, `fmwave`, and `autopanshape` go through `control(name, value)`.
- **Where the reference's JavaScript coercion cannot be held, the bridge differs:** a patternable control given `undefined`, `null`, `true`, or an object (the reference throws a `TypeError` from its parser, or parses `String(value)`; the bridge throws its own message or parses `String(value)`); a numeric string as a `pitchsteps` or `panpath` rate (the reference stores the string; refused here); a string `push` in `drift` (concatenated as text there; read as a number here); a field of `fmVoice` that is not a number (copied as it is there; refused here); a number field of `score` that is not a number (printed as given there, `NaN` here); `fmPresets` keys come back sorted (section 3). None is in the corpus or the suite.
- **The warnings print from the module** with `console.warn` (section 8), one set per instance.
