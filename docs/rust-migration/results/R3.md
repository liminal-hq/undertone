# R3: loading and the bridge skeleton

## Verdict

**Pass with conditions, and marginal for D-17: the orchestrator must stop and ask the person.** The threshold is met as written, but top-level `await` is refused at one common bundler target, so this spike does not decide D-17.

- **Every scratch app builds and runs with at most one documented config line: pass.** Sixteen Vite builds, a no-bundler page, three scripts, and a VitePress site all ran. The one line is `build.target: 'esnext'` (or the narrower `['chrome89', 'firefox89', 'safari15']`), and it is needed only at **Vite 5's default build target**. Vite 8 needed none; Node, Bun, Deno, and a plain dynamic `import()` needed none.
- **Top-level `await` is refused at Vite 5's default target: the marginal part.** Vite 5.4.21 with no config fails with `Top-level await is not available in the configured target environment ("chrome87", "edge88", "es2020", "firefox78", "safari14" ...)`. That is the Vite that VitePress 1.6.4 pulls, so **this repository's own documentation site and playground build on it** and would fail the same way (reproduced with a scratch VitePress site). Under the fail rule in RF-10 this goes to the person.
- **The five graphs equal the TypeScript's byte for byte: pass.** All five programs produced graphs that are string-equal to the layer 3 corpus and to a live run of the reference engine, with no tolerance needed (the pan-law case runs `cos`, `sin`, and `pow` through the `libm` back-end and still matched at nine digits). A negative control (a changed gain) made all five differ, so the comparison does detect differences.
- **The first `play()` after import is booked on time: pass, on a recording and an offline context.** The booked start equalled the context's `currentTime` in every run (all 36 app and browser pairs of 5 loads each, and all 33 script runs). A realtime `AudioContext` was not used (see "What was not verified").

**What is stubbed** (this is a skeleton): there is no engine. The Rust side parses `note('a3')` and queries it with the R1 pattern core, converts the pitch, and then **hand-writes the booking of five voices** (the envelope, an oscillator, a low-pass filter envelope, the stereo panner, a pan path, and a pan law) as a flat list of operations, in the order the TypeScript engine calls Web Audio. The TypeScript side (`replay`) makes exactly those calls on the caller's context. There is no `VoiceParams` resolver, no scheduler, no effects, no autopan, no surround, and no worklet module. Only the five programs are covered.

Installs used `bun install --ignore-scripts`.
- **Runtimes:** **Node v22.21.1** (the plan says Node 20), **Bun 1.4.4** (the plan says 1.2), **Deno 2.9.8**, **Chromium 149.0.7827.55** (cached `chromium-1228`, headless), **Firefox 153.0** (cached `firefox-1539`, headless; driven by the same `playwright-core` 1.63.0-alpha that R2 used, Chromium by 1.65.1). Pages came from a static server bound to `127.0.0.1`, shut down afterwards. WebKit was not run.
- **The skeleton:** `spikes/r3-bridge/` is its own Cargo workspace (not a member of the root workspace, `Cargo.lock` committed). `src/lib.rs` is the Rust half (`undertone-pattern` for the pattern, `undertone-engine`'s `math` for the pan law). `ts/api.ts` is the wrapper (`note`, the chainable controls, `play`, `replay`). Three entries: `ts/index.ts` (browser, **top-level `await init()`**), `ts/init.ts` (browser, an explicit `init()`, no top-level `await`), and `ts/index.node.ts` (Node, Bun, and Deno: reads the module from disk and calls `initSync`, so no `await` there). `build.sh` builds the Rust, runs `wasm-bindgen`, transpiles the entries with `bun build --no-bundle`, writes a `package.json` whose `exports` maps `"."` to the Node entry under the `node` condition and to the browser entry otherwise, and `"./init"` likewise, then packs with `bun pm pack`. The package is `"private": true`, named `@liminal-hq/undertone` for the test only, and was **never published**.
- **Scratch apps** (`spikes/r3-bridge/apps/`, each a few lines, all importing the packed tarball): `vite5/` and `vite8/` (each a `static` app with `import { note } from '@liminal-hq/undertone'`, and a `playground` app with `import * as api` then `new Function(...names, source)` over every export, as `docs/.vitepress/theme/playground/composer.ts` does), `vite5/init/` (the explicit `init()` alternative), `dynamic/` (no bundler; a dynamic `import()` of the unpacked package), `vitepress/` (a VitePress site whose theme registers a component that statically imports the namespace and evaluates with `new Function`, as the real playground does), and `scripts/` (Node, Bun, and Deno). `build-matrix.sh` builds every Vite app into `apps/out/`; `browser/run.mjs` loads each build in Chromium and Firefox. The shared harness (`shared/run.js`) runs the five programs on a recording context (and hashes the call log with SHA-256), and the first one also on an `OfflineAudioContext`, which it then renders.
- **The five programs** (`apps/scripts/programs.mjs`; each `note('a3')` with the controls shown, one event 0.5 s long, matched to a layer 3 case in `conformance/cases/3/placement.json`): `placement-off-plain` (triangle, gain 0.3, sustain 0.5, release 0.2), `placement-pan-default` (adds `.pan(0.5)`: a stereo panner), `placement-off-filter-envelope` (sawtooth, `.lpf(600).lpenv(1200).lpd(0.2)`: a filter envelope), `placement-pan-law-minus6` (`.pan(0.5).panlaw(-6)`: two gains into a channel merger, with `cos`, `sin`, and `pow`), and `placement-pan-path-ramp` (`.panpath([{ pan: 1, time: 0 }, { pan: -1, time: 0.5 }])`: a pan ramp).
- **The comparison** (`apps/scripts/compare-graphs.ts`, run with Bun): for each program it records the graph three ways with the corpus's own `track` and `describeGraph` (exported from `conformance/recorder/graph.ts` for this, a two-word change): through the bridge on a `FakeAudioContext`, from a live run of the reference `playVoice`, and from the corpus file. The layer 3 rule applies as `CONFORMANCE.md` states it (nine significant digits, with a 1e-15 floor for wave coefficients and gains; byte for byte for the engine's maths on the C library back-end). Here the stricter test of **equal canonical JSON** passed, so neither the tolerance nor the C library rule was needed.
- **Raw data:** `spikes/r3-bridge/results/` (`graphs.txt`, `builds.txt`, `browsers.txt`, `chromium.jsonl`, `firefox.jsonl`, `runtime-*.jsonl`, `runtimes.txt`, `dev-server.txt`).

### Timing (step 4)

The first `play()` after the module is ready costs about 1 to 4 ms and starts at the context's current time in every run (`startTime === currentTime`, so on time). Firefox's timer resolution here is 1 ms (the page was not cross-origin isolated), so its play figures are coarse.

## What failed and why

- **Vite 5 at its default target.** Vite 5's `build.target` default is `'modules'`, which resolves to `['es2020', 'edge88', 'firefox78', 'chrome87', 'safari14']`; esbuild refuses top-level `await` for those targets, so `vite build` stops with an error that names the cause and the targets (it does not name the fix). Vite 6 and 7 were not run (see below).
- **Vite 5 dev server.** Described above: two lines (`build.target`, and `optimizeDeps.exclude` for the wasm URL), the second also needed without top-level `await`.
- **`init` in Node.** The browser `init()` entry calls `fetch` on a `file:` URL, which Node does not support, so it fails in Node (`not implemented... yet...`). The package's `exports` therefore sends the `node` condition to the synchronous entry, for `"."` and for `"./init"` (whose `init()` there is a no-op). Bun and Deno resolve the `node` condition too and passed.
- **No other failure.** No hash differed between runtimes, bundlers, or browsers; no graph differed from the TypeScript.
- **Fallback taken:** none. D-17 is left for the person (below).

## What it changes

**D-17 is not decided here.** The evidence for the person:

| Option                                                                     | What a user does                                                                                                                                           | Evidence                                                                                                                                                                                              |
| -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **A. Top-level `await` in the `.` entry** (the plan's default)             | Nothing in Node, Bun, Deno, a plain page, or Vite 8. Vite 5 users (including this repository's docs) add `build.target: 'esnext'` or the D-08 floor array. | Works in everything tried with at most one build line. `import { note }` then `note('c4').play()` works at once. Costs one documented line at Vite 5's default, and a clear build error otherwise.    |
| **B. An explicit `await init()`**                                          | Every user adds one line, in every environment, and moves any module that calls the API at import time.                                                    | Builds at Vite 5's default with no config, but it is a break for everyone (B1), it does not remove the dev-server line, and the playground would need an `init()` gate. Timings are the same as A.    |
| **C. Both entries** (what this skeleton ships: `"."` and `"./init"`)       | The default import is A; a user who cannot set a target imports `@liminal-hq/undertone/init` and awaits `init()`.                                          | Both built and ran in every app tried. The caveat: the two entries are separate module instances (two WebAssembly instances, handles not shared), so a program must use one or the other, never both. |
| **D. Lazy instantiation** (calls before readiness recorded, then replayed) | Nothing.                                                                                                                                                   | **Not built or measured.** It keeps the `import { note }` shape but defers sound; `play()` would not book at the call, which changes the first-booking test above.                                    |

My reading of the evidence, for the person to take or leave: **A, with the `build.target` line in the install notes and the Moving from 0.3 section, with C's subpath as an escape hatch**, because the plan already sets a browser floor (Chromium 89+, Firefox 89+, Safari 15+) that is exactly where top-level `await` begins, so a Vite 5 user who sets that floor in `build.target` loses nothing the package supports. **The docs site itself needs the one line in `docs/.vitepress/config.mts`** (`vite: { build: { target: 'esnext' } }`) the day the playground imports the bridge, and its `docs:dev` would need `optimizeDeps.exclude`. If the person weighs "works with no config at Vite 5's default" above keeping the 0.4.0 import shape, B is the choice; the cost is that every user changes code.

**Changes for the plan files** (made in this commit set, concisely): `ARCHITECTURE.md`'s Loading bullet notes the conditional exports (a synchronous Node entry; a browser entry) and the build lines, and that D-17 is still open; `DECISIONS.md` D-17 points here. Nothing else needs to change.

**For RF-26 and RF-27:** the replay design held for the five programs. The bridge's wrapper must send **operations, not objects** across the boundary (a flat `Float64Array` of fixed-width records worked and is cheap to replay), the Rust booking must **call Web Audio in the TypeScript engine's order** so node numbering matches (the graphs diff by creation order), and `replay` needs the destination, the channel-merger input count, and the one automated parameter per node kind. A real `VoiceParams` resolver and the full engine are not tested by this skeleton.

## What was not verified

- **Nothing was listened to.** The only audio is a 1 s offline render of the first program in Chromium and Firefox, checked for a non-zero peak (0.298 and 0.299; the small difference is the two browsers' oscillators, not a graph difference). No perceived sound quality was judged.
- **A realtime `AudioContext`.** "On time" is the booked start equalling `currentTime` on an `OfflineAudioContext` and on recording contexts. A running context's user-gesture and autoplay rules, the scheduler's lookahead, and `currentTime` advancing between the call and the booking were not exercised.
- **WebKit and Safari** (not runnable here). Safari 15 is the stated floor; top-level `await` is specified there, but the bridge was not loaded in it.
- **Other bundlers and versions:** Vite 6 and 7, webpack, Rollup (alone), esbuild (alone), Parcel, Next.js, and Bun's own bundler were not run. Vite 7's changed default target is from memory, not measured. The `docs:dev` server was not run with VitePress (only the Vite 5 dev server on a scratch app).
- **Server-side rendering paths:** the VitePress build prerendered the page without error, but which entry the server bundle loaded (the `node` entry or the browser one) was not checked.
- **The plan's floors:** Node 20, Bun 1.2, and Deno 1.x were not run (Node 22.21.1, Bun 1.4.4, Deno 2.9.8 were).
- **The module's size and speed** under `wasm-opt` and the real engine (R4), a real `VoiceParams` resolver, effects, autopan, surround, rendering, the scheduler, and the worklet module (compiled on the main thread and posted, as `ARCHITECTURE.md` plans) were not part of this skeleton.
- **Timings** are one machine, local files, cold start, medians of 5 (browsers) or 11 (scripts) runs; Firefox's resolution is 1 ms.
