# R2: closures and handles across WebAssembly

## Verdict

**Pass with conditions.** The closure design holds, the foreign leaf is cheap, and nothing leaks, but the garbage collector cannot be relied on to free pattern handles promptly, so the spec's fallback applies.

- **Closure chains: pass.** Over 1,000 queries of `every`, `jux`, and `every` plus `jux` chains there were **0 calls from WebAssembly into JavaScript and 0 user callbacks**, in all five runtimes that ran (Node, Bun, Deno, Chromium, Firefox).
- **Foreign leaf: the cost of the leaf passes, the total as written fails.** A 32-hap `fmap` leaf adds about 3 to 8 µs to a query (under 20 µs everywhere). The whole 32-hap query, with or without the leaf, takes 65 to 100 µs in V8 and JavaScriptCore runtimes and about 400 to 470 µs in Firefox, so "a 32-hap foreign leaf under 20 µs median" is not met if read as the whole query. The time is the R1 core's query (about 2 µs a hap in WebAssembly), not the boundary: a pattern whose query is a JavaScript function (`new Pattern(query)`) returning the same 32 haps takes 12 to 15 µs. This does not trigger the interpreter fallback (RF-25's extra week); it is a finding for the core's query speed (see "What it changes").
- **Handles: fail as written, fallback taken.** With no explicit collection and an idle page, between 40,000 and 160,000 dead handles (up to 16% of the million built) stayed alive for the whole ten seconds in Node, Deno, and Chromium (some repeats), and in Firefox about half to nearly all of them (up to 94%) did in two of three repeats, even with allocation churn. Memory after settle climbed over three repeats in Node, Bun, Chromium, and Firefox. The cause is not a leak: with a collection at every `await` in the loop, all five runtimes that can collect on demand (Node, Bun, Deno, Chromium; Firefox cannot be asked to) stayed flat at 3.6 MB over five repeats with live handles back to 0 or 1. The collector simply does not know that a handle holds WebAssembly memory, so it runs when the JavaScript heap says so. The fallback is therefore taken: an opt-in `free()` and a `Symbol.dispose` method on patterns (an addition, not a break); the garbage-collected path stays the default.
- **WebKit was not run.** See "What was not verified".

This file and the status-log row are committed after them.

The wasm was served from a localhost-only static server on `127.0.0.1` (cross-origin isolated, so `performance.now()` has a fine resolution), shut down afterwards.
- **Layout:** `spikes/r2-handles/` is its own Cargo workspace (`[workspace]`), not a member of the root workspace; its `Cargo.lock` is committed. Git and Prettier ignore `spikes/**/{target,node_modules,pkg,out}`; ESLint ignores `spikes/**` (type-aware lint of throwaway code is not worth the setup; Prettier still checks the hand-written files).
- **What the harness does.** `ts/wrapper.ts` is the `Pattern` class over a `Handle`; `every(n, fn)` and `jux(fn)` run `fn` in TypeScript at construction and pass the resulting handle to Rust, which stores it in an `Every` node or a `Stack` of two `WithControl` nodes (R1's own nodes). `fmap(fn)` builds a `Foreign` node and `new Pattern(query)` a `Custom` node, each holding the JavaScript function. The wrapper swaps `WebAssembly.Instance` while `initSync` runs so that every import is wrapped and counted (`counters.imports`); user functions count separately (`counters.callbacks`). The live-handle count is a Rust counter incremented when a `Handle` is made and decremented in its `Drop`, so it counts real frees by wasm-bindgen's finalizer.
- **Settle modes (step 3).** The pass criterion says "within ten seconds of the loop ending". A garbage collector runs when something allocates, so three ways to wait are recorded: **idle** (the harness only sleeps in 100 ms steps), **churn** (it also allocates about 1.6 MB of JavaScript garbage every 100 ms, as a running application would), and **gc** (it calls the runtime's explicit collector every 100 ms). A fourth run, **leak**, also collects at every `await` in the loop and does five repeats. A repeat is "settled" when live handles are within 1% of the million built (10,000) of the count before the first repeat (20); the 20 are the fixed handles of the harness.
- **Raw data:** `spikes/r2-handles/results/<runtime>-<mode>.json`.

**Why memory climbs without help.** WebAssembly memory only grows. The high-water mark is set by how many handles are alive at the worst moment, and that depends on how late the collector runs; it can rise from one repeat to the next as the collector's timing varies, and it never falls. It is not a leak (the leak check is flat), but it is a monotonic climb as written.

## What failed and why

- **Handles are not freed promptly by the collector (the fallback in the spec applies).** Garbage collectors are driven by the size of their own heap. A `Handle` is a few dozen bytes of JavaScript that own tens or hundreds of bytes of WebAssembly memory, so the collector does not see the pressure, and `FinalizationRegistry` callbacks run only after a collection. Idle pages, and in Firefox even busy pages, can keep hundreds of thousands of dead handles for more than ten seconds and let memory climb. **Fallback taken:** an opt-in `free()` and a `Symbol.dispose` method on pattern wrappers (so `using p = ...` works), documented; the garbage-collected path stays the default and is correct, only lazy. The spike's wrapper already carries `free()` and was not used by the loop, which is what is measured. Engines, players, and loop handles keep their explicit `free()`.
- **The 32-hap total is above 20 µs.** The foreign leaf itself is cheap, so the interpreter-in-the-bridge fallback (RF-25, +1 week) is **not** taken and D-06 keeps `new Pattern(query)` and per-query `fmap`. The speed of the core's query is a separate matter (see below).
- **Firefox is slower on the same module.** A 32-hap query takes about six times as long as in Chromium, and its collector lagged most (up to 94% of a million handles alive at the end of a loop, memory up to 292 MB). It was run as a headless build driven by Playwright's patched Firefox, which may differ from release Firefox; no other Firefox was tried.
- **Playwright and the cached builds.** The cached Firefox build did not speak `playwright-core` 1.65.1's protocol, so a 1.63 alpha already on the machine was used for it; Chromium worked with 1.65.1 by path.

## What it changes

Edited in this pull request, concisely:

- [API-MAPPING.md](../API-MAPPING.md): the freeing bullet now says pattern wrappers get an opt-in `free()` and `Symbol.dispose` (an addition, not a break), with the reason, and that the default is still the garbage collector.
- [ARCHITECTURE.md](../ARCHITECTURE.md): the bridge diagram's wrapper box says "or freed explicitly".

Not edited, for the orchestrator and `DESIGN-ADJUSTMENTS.md`:

- **RF-24 and RF-25:** add `free()` and `[Symbol.dispose]()` to the bridge `Pattern`; document that dropping a pattern frees it when the runtime collects, and that long loops that build patterns (live coding, generative sets) should call `free()` or use `using`. A test should build and drop a million handles with and without it.
- **The core's query speed:** about 2 µs a hap in WebAssembly (R1's tree, `i128` fractions) is the largest part of a 32-hap query. RF-13 or a performance work package should profile `Pattern::query` natively and in WebAssembly before M6; a typed fast path for small fractions is the likely fix. This does not block M3.
- **RISKS.md:** the note about memory could add "wasm memory only grows; peak handle count sets the high-water mark".
- **D-06:** unchanged (keep `new Pattern(query)` and `fmap`); no new break.

## What was not verified

- **Nothing was listened to.** This spike builds and queries patterns; it makes no sound.
- **WebKit was NOT run.** About 48 GB was free, so `playwright-core install webkit` was tried (Playwright 1.65.1, build `webkit-2388`, about 278 MB); it downloaded but would not start because the machine lacks system libraries it needs (`libicu` 74, `libxml2.so.2`, `libjxl.so.0.8`, `libbacktrace`) and installing system packages was out of scope. The download was removed. No Safari or WebKit number appears in this file and none is guessed.
- **Node 20 and Bun 1.2 were not run:** Node 22.21.1 and Bun 1.4.4 were used.
- **Firefox and the explicit collector:** Firefox was run with idle and churn only; no explicit-collection or leak run exists for it.
- **Native timing of the core was not measured**, so the split of the 2 µs a hap between WebAssembly and the algorithm is not known.
- **`free()` and `Symbol.dispose` were not run in the loop.** The spike measured the collector only; the opt-in path is the spec's fallback and is not tested here beyond existing in the wrapper.
- **Each repeat is in one process and one module instance,** after the same warm-up; one machine, no battery or throttling variation, and the browsers were headless. Timings vary between runs of the same step by several percent (see the ranges).
- **The 1% criterion was applied to the count before the first repeat** (20 live handles), because "the start" of a repeat that begins with garbage left by the last one would excuse it.
