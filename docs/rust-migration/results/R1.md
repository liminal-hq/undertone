# R1: the pattern and signals core

## Verdict

**Pass with conditions.** A node-tree pattern crate built from the TypeScript reproduces the layer 1 corpus exactly, signals included, with no closure in the tree outside the two escape hatches. The conditions:

1. **One program is not covered:** `notes-chord-01` (`chord()` and `voicing()`), which needs `chord.ts` and belongs to the chords group (RF-15). The other 308 of 309 are equal. The RF-07 subset the plan names (300 programs) is covered in full; the corpus as recorded holds 309 layer 1 programs.
2. **The reference's `**` is JavaScriptCore's, not the C library's.** `2 ** -0.5` is `0.7071067811865475` in Bun and `0.7071067811865476` in glibc, so one corpus program (`notes-scale-04`) failed until `js::pow` copied the rule (an exponent of `-0.5` is `1 / sqrt(x)`). This is a finding for R9 and the engine: maths must follow the reference's engine, not the platform's.
3. **Layer 1 floats are compared within a tolerance (D-23).** With `libm` as the default maths, 5 of the 308 covered programs differ from the recording by one unit in the last place and pass only through the 1e-14 tolerance; see the addendum. The `no_std` claim of D-18 now holds.

## Addendum: D-23 (libm everywhere), no_std, and a tolerant float comparison

After the spike's first run, decision D-23 put the maths on `libm` everywhere. `undertone-pattern` now has a default `libm` feature (`libm` 0.2.16, the engine's pin) for `floor`, `sin`, `cos`, `pow`, and `sqrt`, with the standard library's maths kept behind `--no-default-features --features std`. `js::pow` still applies JavaScriptCore's `x ** -0.5 = 1 / sqrt(x)` rule. Commits: `441fe96` (tolerant comparison) and `9cd87d8` (libm default).

- **Layer 1 floats compare within a tolerance, by D-23.** Fractions, strings, structure, hap counts, and `whole` and `part` are exact; a float is equal if its text is identical, within a relative 1e-14, or within an absolute 1e-15 near zero (the layer 3 floors). Tests show a number off by 1e-9, a wrong fraction, a missing hap, a wrong string, and a changed special value still fail.
- **Result with `libm`: 308 of 309 equal, 303 exactly and 5 only through the tolerance** (`notes-scale-03`, `notes-scale-05`, `signals-sine-rev-01`, `signals-sine-every-01`, `signals-rangex-01`; groups `notes` 2 and `signals` 3), each one unit in the last place. With the standard library's maths all 308 are exact. The one program not covered is still `notes-chord-01`.
- **Properties:** 70,000 cases passed again with the `libm` default, 0 failures.
- **`no_std` (D-18) now holds for the pattern crate.** `cargo build -p undertone-pattern --no-default-features --features libm --target thumbv7em-none-eabi` builds. It needed small changes only (`#![no_std]` unless `std`, `core::error::Error`, test-module imports), well under half a day. Without either feature the crate refuses to build with a message. Not run: the tests on the bare-metal target (they need `std`), and no size or speed was measured.

**How equality is decided.** The Rust haps are sorted as the recorder sorts them, written as the corpus's own compact JSON, and compared as text. Fractions are `n/d` text. A number is the text JavaScript prints, so a one-bit float difference, a sign of zero, or a different layout fails. The test also fails if the not-covered list or the corpus size changes. Query errors and program errors are compared word for word. Signal `samples` are compared the same way.

**The seven properties:** window independence of discrete programs; window independence of signals given structure (`segment`, `euclid`, and as `gain`); `fast(n).slow(n)`; `rev().rev()`; `every(1, f)`; a signal read at a point is the same in any window (except a reversed signal, which the reference's own tests exclude); `seed(s)` is reproducible across builds and threads. Programs are JSON in the corpus language, depth at most 5, run by the same interpreter as the corpus.

## The tree as built

| Node                 | Holds                                      | Sampler (`has_sampler`) | `sample(t)` (the pass-through table)                    |
| -------------------- | ------------------------------------------ | ----------------------- | ------------------------------------------------------- |
| `Silence`            | nothing                                    | no                      | none                                                    |
| `Pure(v)`            | a value                                    | no                      | none                                                    |
| `Stack(ps)`          | children                                   | any child               | first child with a value at `t`                         |
| `Cat(ps)`            | children                                   | any child               | child `floor(t) mod n` at `t - offset`                  |
| `Compress{b, e, p}`  | a window and a child                       | the child's             | inside the window `p` at the mapped time, outside none  |
| `Fast` / `Slow`      | a factor and a child                       | the child's             | child at `t * f` or `t / f`                             |
| `Rev(p)`             | a child                                    | the child's             | child at `c + (c + 1 - t)` for the cycle `c`            |
| `Every{n, base, tf}` | the pattern and its transformed copy       | either's                | the pattern picked for `floor(t)`                       |
| `Arrange(sections)`  | cycle counts and children                  | any section             | the section for `floor(t)` at `t - offset`              |
| `Map{p, f}`          | a child and a `MapFn` (named map)          | the child's             | the child's value with `f` applied                      |
| `Arith{l, op, r}`    | two children and an operation              | the left's              | left at `t`, then right at `t` (none if either is none) |
| `Signal(kind, seed)` | a kind (shape, rand, perlin, ...) and seed | yes                     | the signal's value at `t`                               |
| `Sample` / `Segment` | a source and a boolean structure pattern   | no (query-only)         | none; they read the source at each onset                |
| `WithControl`        | child, a control, a literal or a pattern   | no (query-only)         | none; it reads the control at each onset                |
| `Degrees(p)`         | a child                                    | no (query-only)         | none                                                    |
| `Foreign{p, f}`      | a child and a host function (escape hatch) | the child's             | child, then the host function                           |
| `Custom(q)`          | a host query (escape hatch)                | as the host says        | the host's                                              |

The table is what RF-07 step 3 asked for: the reference's sampler passes through `fast`, `slow`, `rev`, `range`, `fmap`, `cat`, `seq`, `timecat`, `stack`, `arrange`, and `every`, and each of those is a row above (`seq`, `timecat`, and `euclid` on a pattern are `Stack` of `Compress`; `range` is a `Map`). `has_sampler` is computed once when a node is built, so it costs nothing at query time.

**Design decisions worth carrying forward.**

- **Closures at construction.** `every(n, f)` and `jux` take a Rust closure that runs once, while the pattern is built, and the tree keeps the pattern it returned. Nothing in the tree calls back. That is what makes a tree printable, hashable, and sendable.
- **Named maps.** `fmap`, `range`, `scale`, and voice patches are `MapFn` data; a value type says how to apply one (`Datum::apply`). This replaces `Arc<dyn Fn>` everywhere except the one `Foreign` node.
- **Values are generic.** `Pattern<T: Datum>` with `Value` (number, string, boolean, map) for voice patterns, `f64` for numeric signals, and `bool` for the structure inside `segment`. `WithControl` and `Degrees` are generic nodes that go through `Datum` methods, so they exist for every `T` but only mean something for `Value`. RF-14 may prefer to type that split properly.
- **Random signals rebuild from data.** `seed()` makes a new `Signal` node with another seed; the reference's registry of re-seed closures is not needed.
- **Arguments are JavaScript numbers (`f64`) in the pattern API** (`fast`, `every`, `euclid`, `arrange`, `timecat`, `segment`), because the reference's error messages quote the number it was given (`every() cycle count must be a positive integer, got 1.5`) and the corpus holds those cases. RF-13 may narrow them to integers in a typed Rust API and keep the f64 forms in the bridge.

## What failed and why

- **`notes-scale-04`** failed on the first run by one unit in the last place (`311.12698372208087` against `311.1269837220809`). Cause: JavaScriptCore's `**` with an exponent of `-0.5` is `1 / sqrt(x)`, while glibc's `pow` is correctly rounded. Checked in Bun over bases 2 to 199: `x ** -0.5` equals `1 / Math.sqrt(x)` every time, while glibc's `pow` differs from that in 47 of 198 cases; for `2 ** (k / 12)` over `k = -60..60` the only mismatch with glibc is `k = -6`. Fallback taken: `js::pow` special-cases `y == -0.5` for positive finite `x` and otherwise calls the C library.
- **The `sin` and `cos` of the periodic signals matched on the first run** for every recorded sample (100 signal programs with samples at seven instants each). That is evidence, not proof, that the C library's trigonometry agrees with JavaScriptCore's at those points; R9 should test the wave tables, which use far more.
- **The doc tests of `rev` and `every`** assumed hap order. A query returns haps in the order the tree produces them, not time order (the recorder sorts), so the examples sort. The commit `baf1d7f` was made before that doc-test step finished; `6ed1c9e` fixes it, and every later commit passes the whole gate.

## What it changes

- **[ARCHITECTURE.md](../ARCHITECTURE.md) and RF-13 to RF-16:** the node-tree design stands; no node needs the `Arc<dyn Fn>` fallback, so signals can be built-in nodes and the worklet can query them (RF-16, RF-29). RF-13 can start from this crate (the result says the code passes review for keeping as the start of RF-13, subject to the person's review): `Fraction`, `Span`, `Hap`, `Pattern`, the nodes, `mini::parse`, `js`, signals, and the first controls.
- **`undertone-pattern` and `no_std` (D-18):** superseded by the addendum: with the `libm` default the crate builds for `thumbv7em-none-eabi`. Before D-23 it failed on five maths functions behind `src/math.rs`; that module now has the `libm` and `std` back-ends.
- **R9 and CONFORMANCE.md:** add "`**` follows JavaScriptCore (`-0.5` is `1 / sqrt`)" to the maths findings, and check `Math.sin`, `Math.cos`, `Math.exp`, and `Math.pow` of the engine against `libm` on the engine's inputs, not only on these.
- **Decisions D-13:** `i128` fractions were enough for everything in the corpus and the properties, with checked arithmetic that panics on overflow rather than wrapping.
- **API-MAPPING.md:** no change to names. Note for RF-14: control methods here are `control(Control, ControlArg)`; the named methods (`gain`, `lpf`, ...) come with the full control table.

## What was not verified

- **Nothing was listened to.** This spike reads no audio and produces none; a hap is a value in a list.
- **`chord()` and `voicing()`** are not implemented (one corpus program). The other `Pattern` methods that exist in the reference (the rest of the controls, `panpath`, `autopan`, `fm*`, `hpf`, `room`, `delay`, `play`, `loop`, `render`, `voice`, `channels`, `surround`) are not implemented and are not in this corpus subset; the interpreter reports them as "not covered" rather than guessing.
- **Layer 2** (resolved `VoiceParams`) is RF-14. `Datum::with_number` and `MapFn::Merge` only set field names on a value map.
- **The `mini` group** (the three leaf rules `word`, `pitch`, `drum`, six spans, error positions) is not recorded in the corpus yet. Error positions are unit-tested, including a character outside the Basic Multilingual Plane, but only against what the TypeScript source says, not against recorded cases. A lone surrogate half in an error message shows as U+FFFD, because a Rust string cannot hold one; the reference's message would contain the lone half.
- **Number parsing of leaf words** uses the grammar of JavaScript's `Number()` as written in `js::string_to_number`, tested against a table, not against the engine over all inputs. `toLowerCase` for scale names uses Rust's Unicode lowercasing.
- **Performance** was not measured, nor memory, nor deep patterns (nesting beyond 5 levels, or thousands of cycles in one query). Debug builds only.
- **Overflow:** a query over a very long span with fractional time could exceed `i128` and panic; nothing in the corpus or the properties reaches it.
- **The 70,000 property cases** use fixed grammars; they did not find a failure, which is evidence and not a proof. The reference's own `fast-check` run (300 cases) is separate.
